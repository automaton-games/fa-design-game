# 公開識別子にslugとcodeを使用する

コンテストと問題をURLから参照する公開識別子には、データベースの内部主キーと同じ `id` ではなく、コンテストに `slug`、問題に `code` を使用する。コンテストの `slug` はすべてのコンテスト間で一意とし、問題の `code` は同じコンテスト内で一意とする。これにより、APIの公開識別子と将来導入するデータベースの内部主キーを名前で区別し、それぞれの値が有効な範囲を明確にする。

## 検討した選択肢

- コンテストと問題の公開識別子を、どちらも `id` と表記する
- コンテストの公開識別子を `slug`、問題の公開識別子を `code` と表記する

## 判断理由

`id` に統一するとAPIの表記は単純になるが、公開識別子とデータベースの内部主キーを名前から区別できない。将来、数値の内部主キーを導入すると、同じコンテストに公開用の `id` と内部用の `id` が存在し、API、アプリケーション、データベースのどの識別子を指しているのかが文脈に依存する。

コンテストの公開識別子はURLでコンテストを指定する安定した文字列であり、システム全体で一意になる。一方、問題の公開識別子はコンテスト内で問題を識別するコードであり、異なるコンテスト間で重複できる。この性質の違いを名前に反映できるため、コンテストに `slug`、問題に `code` を採用する。

## メリット

- APIの公開識別子とデータベースの内部主キーを、名前から判別できる
- `slug` と `code` の一意性の範囲が明確になり、問題を `(contest_id, code)` で管理するデータモデルと対応する
- 変数名とルートパラメータ名から値の役割を判断できるため、実装時に異なる識別子を取り違えにくい
- データベースの内部主キーを変更しても、公開URLとAPIの識別子を維持できる

## 影響

APIレスポンスでは、コンテストの公開識別子を `slug`、問題の公開識別子を `code` として返す。APIとフロントエンドのルートパラメータには、それぞれ `contestSlug` と `taskCode` を使用する。公開URLの値とパス構造は変更しない。
