# 構造検証と提出検証の責務境界

DFAの検証を、問題に依存しない「構造検証」と問題固有の「提出検証」に分離する。

構造検証（DFAドメイン層、#22）はDFA単体の不変条件のみを担う。提出検証（提出層）は問題の存在と問題固有の提出制約のみを担う。alphabet系の検査は提出DFAには現れず、問題データローダが担う（ADR 0001）。

## 構造検証が保証するDFAの不変条件

- `states` は1以上の状態名からなり、重複・空文字・空白のみを許さない
- `start` は空でなく `states` に含まれる
- `accept` の各要素は `states` に含まれ、重複しない
- 遷移はすべての `state × symbol` について定義される（完全関数）
- 各遷移先は `states` に含まれる
- 余分な遷移（`states` にない状態、または問題の alphabet にない記号に対する定義）は構造エラーとし、無視しない

## 提出検証が扱う条件

- 対象問題が存在すること
- 問題固有の提出制約（状態数上限など）

## 考慮した選択肢

- 構造検証に問題固有条件（alphabet 整合・状態数上限）も含める。
  却下: 問題に依存する条件をDFAドメイン層へ持ち込むと、#22 が問題データへ結合し再利用性が下がる。alphabet は問題が所有する（ADR 0001）ため、提出DFAの構造検証には現れない。

## 帰結

- #22 の検証は、重複・空文字状態名・余分遷移の検出を追加して拡張する必要がある。#58 の設計は #22 の拡張を要求する。
- `Validate` は問題の alphabet を注入して構造検証を一つの操作として行う（遷移の完全性は問題の alphabet で測るため）。注入と検証を分けないことで、`ValidatedDFA` の構築を検証経由に限定できる。
- 検証済みDFAは構造検証を通過したことが保証されるため、等価性判定と提出検証は構造の再検証を行わない。
