# 構造検証と提出検証の責務境界

DFAの検証を、問題に依存しない「構造検証」と問題固有の「提出検証」に分離する。

構造検証（DFAドメイン層、#22）は入力アルファベットを含むDFA単体の不変条件を担う。提出検証（問題・提出層）は問題の存在と問題固有の提出制約のみを担う。入力アルファベットは提出JSONには現れないが、問題データから構造検証へ渡す（ADR 0002）。

## 構造検証が保証するDFAの不変条件

- 入力アルファベットは1以上で、重複・空文字・空白のみの入力記号を許さない。複数文字の入力記号は許可する
- `states` は1以上の状態名からなり、重複・空文字・空白のみを許さない
- `start` は空でなく `states` に含まれる
- `accept` の各要素は `states` に含まれ、重複しない
- 遷移はすべての `state × symbol` について定義される（完全関数）
- 各遷移先は `states` に含まれる
- 余分な遷移（`states` にない状態、または問題の alphabet にない記号に対する定義）は構造エラーとし、無視しない

## 提出検証が扱う条件

- 対象問題が存在すること
- 問題固有の提出制約（状態数上限など）

提出検証は`Store.Judge`を単一の入口とし、その内部で問題存在を確認し（HTTP `404`）、問題固有制約を検証する（HTTP `422`）。HTTP handlerは検証順序を組み立てない。

## 考慮した選択肢

- 構造検証に問題固有条件（状態数上限など）も含める。
  却下: 問題に依存する条件をDFAドメイン層へ持ち込むと、#22が問題データへ結合し再利用性が下がる。入力アルファベット自体の妥当性はDFAの不変条件なので構造検証に含めるが、その値の所有元は問題データとする。

## 帰結

- #22 の検証は、重複・空文字状態名・余分遷移の検出を追加して拡張する必要がある。#58 の設計は #22 の拡張を要求する。
- `Validate`は問題の入力アルファベットを受け取り、その妥当性確認、注入、DFA本体の構造検証を一つの操作として行う。注入と検証を分けないことで、`ValidatedDFA`の構築を検証経由に限定する。
- 検証済みDFAは構造検証を通過したことが保証されるため、等価性判定と提出検証は構造の再検証を行わない。
